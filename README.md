## Issue 01：起動・設定・運用手順

### 構成

- 同じWanbotを本番・テストサーバーで使用する。
- 原則1プロセスで起動し、同じトークンで二重起動しない。
- 本番設定は `PROD_`、テスト設定は `TEST_` で区別する。
- 同じプロセスのため、再起動や共通部分の障害は両サーバーに影響する。

### 初回セットアップ

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
```

`.env.example`を`.env`へコピーし、トークンと必要な設定を記入する。
既存の`.env`は上書きしない。

```bash
chmod 600 .env
```

`.env`、運用データ、生成ログはGitへ追加しない。

### 設定

- `DISCORD_TOKEN`：Wanbotのトークン。
- `PROD_GUILD_ID` / `TEST_GUILD_ID`：参加先サーバー。
- `PROD_ADMIN_ROLE_IDS` / `TEST_ADMIN_ROLE_IDS`：Wanbotの管理者ロール。
- 管理者ロールはカンマ区切りで複数指定できる。
- `ENABLED_FEATURES`が空欄なら、そのサーバーの業務機能は無効。
- 設定変更は再起動で反映する。

現段階では業務機能は未実装のため、両方の`ENABLED_FEATURES`を
空欄にし、`DM_FORWARD_ENABLED=false`を維持する。

### 設定形式の確認

```bash
python -m wanbot --check-config
```

このコマンドはDiscordへ接続しない。
IDの実在・所属・Botの権限は、接続後に別途確認する。

### 起動・停止

```bash
python -m wanbot
```

停止は `Ctrl+C`。

起動時にサーバーと入力済みのロール・カテゴリ・チャンネルを確認する。
有効な機能に必要なBot権限も確認する。
現在は設定先の検証に失敗すると起動を停止する。

### 接続確認専用の起動

```bash
python -m wanbot.connection
```

業務機能を無効にした状態で使用する。

### 動作確認コマンド

テストサーバー限定で `/wanbot_status` を登録する。
指定された管理者ロールのメンバーだけが実行でき、
結果は実行者だけに表示される。

現段階のコマンド同期はテストサーバーのみ。
本番の業務コマンドは、各機能の実装時に追加する。

### テスト・コード検査

```bash
python -m pytest -q
python -m ruff check wanbot tests
```

自動テストは実際のトークンやDiscord接続なしで実行する。

### ログ

- 時刻はUTCで記録する。
- トークンを伏せ、一般ログへ回答・DM本文を渡さない。
- 例外本文ではなく、例外の種類と処理名を記録する。
- 現段階では標準出力へ出力する。

### 後続Issueで追加するもの

- 業務機能本体と、そのコマンド登録。
- サーバー別の運用データ保存・復元。
- 管理者専用チャンネルの閲覧範囲の検証。
- ルール投稿やリアクションの検証。
- 各操作直前の権限・ロール順位の再確認。
- 全キック共通の管理者承認フロー。

機能の実装時は、設定上の有効化だけでなく、
実際の起動状態と操作者の権限を確認して処理する。

## Issue 02：サーバー別データ保存

### 保存先

`.env` の `RUNTIME_DATA_DIR` 配下に、サーバーID別で保存する。

```text
runtime/
  <本番サーバーID>/
    welcome.json
  <テストサーバーID>/
    welcome.json
```

同じユーザーが両サーバーにいても、保存データを共有しない。
未登録のサーバーには保存できない。

### 保存形式

```json
{
  "schema_version": 1,
  "guild_id": 200,
  "document": "welcome",
  "data": {}
}
```

- `schema_version` は共通保存形式のバージョン。
- `guild_id` と `document` が保存先と一致するか確認する。
- `data` は文字列キーの辞書。
- ユーザーIDを辞書のキーにする場合は `str(user_id)` を使う。
- 質問回答や予約など、機能固有のデータ構造の検証は各機能で実装する。

### 同期版と非同期版

- `GuildJsonStore`：同期的な読み書きの共通処理。
- `AsyncGuildJsonStore`：Discordの非同期処理から使う窓口。

Discordのイベントやコマンドからは、原則として非同期版を使用する。

```python
from wanbot.storage.async_store import AsyncGuildJsonStore

async def example(config, guild_id):
    async with AsyncGuildJsonStore(config, guild_id, "welcome") as store:
        current = await store.read()

        def change(data):
            data["example"] = {"step": "waiting"}
            return data

        await store.update(change)
```

常設の機能では、機能開始時に保存窓口を作り、
停止時に `await store.close()` を呼ぶ。

### 更新時の注意

- 更新は `update()` の中で最新データを読み、変更して保存する。
- `read()` で取得した辞書を変更しただけでは保存されない。
- 更新関数は通常の `def` で作る。
- 更新関数の中でDiscordへの通信や長時間の処理を行わない。
- 外側の古い読み取り結果で全体を置き換えると、更新を失う可能性がある。
- 呼び出し元がキャンセルされても、開始済みの保存は継続する。
- キャンセル後の再実行前には、保存状態を確認する。

### 安全性と制限

- 一時ファイルへ書き終えてから、本来のファイルと置き換える。
- 壊れたJSONや未対応の保存形式を勝手に初期化しない。
- 保存先のサーバーフォルダー・ファイルにシンボリックリンクを許可しない。
- 同じプロセス内の更新を、ファイル単位で順番に実行する。
- 非同期版は、同じイベントループ内で使用する。
- 同じデータを複数プロセスから同時更新する用途には対応しない。
- 強制終了や停電時の完全な永続化、バックアップは別途対策が必要。
- `close()` は開始済み処理の終了を待つ。保存失敗はログに記録される。
- 通常の更新呼び出しでは、保存失敗の例外を呼び出し元へ返す。

### 復元の範囲

この基盤で保存データを読み戻せる。
Welcomeの進行状態、予約、ボタン、期限などを読み戻して
実際の動作へ復帰させる処理は、各機能のIssueで実装する。

### テスト

一時ディレクトリと架空のデータを使用する。
実際の運用データやDiscord接続は使用しない。

```bash
python -m pytest -q
python -m ruff check wanbot tests
```

## VALORANT診断と診断ログ

### 有効化

同じWanbotで本番・テストサーバーを扱います。
診断を利用するサーバーの `ENABLED_FEATURES` に
`valorant_diagnosis` を指定してください。

テストサーバーだけで有効にする例：

```dotenv
PROD_ENABLED_FEATURES=
TEST_ENABLED_FEATURES=valorant_diagnosis
TEST_VALO_DIAGNOSIS_TIMEOUT_SECONDS=1800
```

ほかの機能も指定済みの場合は、既存の機能名を残して
カンマ区切りで追加してください。

各サーバーの以下の設定も必要です。

- `PROD_GUILD_ID` / `TEST_GUILD_ID`
- `PROD_ADMIN_ROLE_IDS` / `TEST_ADMIN_ROLE_IDS`

管理者ロールはカンマ区切りで複数指定できます。
Discordの「管理者」権限だけでは、診断コマンドの実行を許可しません。

回答期限は次の設定で指定します。

- `PROD_VALO_DIAGNOSIS_TIMEOUT_SECONDS`
- `TEST_VALO_DIAGNOSIS_TIMEOUT_SECONDS`

単位は秒で、未設定時は1800秒です。
診断開始からの期限であり、回答やBot再起動では延長しません。
Welcome全体の期限とは別の設定です。

設定変更後はBotを再起動してください。

### 診断DMの送信

診断を有効にしたサーバーで、設定された管理者が実行します。

```text
/valo_role member:対象者
```

対象者に説明文と15問の診断をDMで送信します。
本人だけが回答でき、回答後の変更はできません。

- 進行中なら、現在の質問を再送します。
- 完了済み、または期限切れなら、新しい診断を開始します。
- 回答完了後は結果を保存し、結果表示から回答ボタンを取り除きます。

### 質問・結果の再表示

```text
/valo_role member:対象者 resend:True
```

新しい診断は開始しません。

- 期限内の診断が進行中なら、現在の質問を再表示します。
- 結果保存待ちなら、保存処理を再実行して結果を表示します。
- 進行中の診断がなく、保存済みの結果があれば、その結果を再表示します。
- 期限切れの診断は再開しません。通常の送信で新しく開始してください。

### 管理者による回答確認

```text
/valo_role_log member:対象者
```

退出済みの人などは、ユーザーIDでも指定できます。

```text
/valo_role_log user_id:対象者のユーザーID
```

`member` と `user_id` は、どちらか一方だけを指定します。

実行した管理者だけに、最新の診断結果・スコア・完了日時と
全15問の質問・回答を表示します。
「前へ」「次へ」でページを切り替えられます。

ページ操作時にも、実行者本人であることと管理者ロールを確認します。
5分間操作しなかった場合やBot再起動後は、コマンドを実行し直してください。

### 保存と再起動

運用データは、設定した保存先のサーバーID別フォルダーに保存します。

- `valorant_sessions.json`：進行中、または結果保存待ちの診断
- `valorant_diagnoses.json`：各ユーザーの最新の診断結果

再診断すると、そのユーザーの最新結果を更新します。
すべての診断履歴を蓄積する仕様ではありません。

Bot起動時に、期限内の診断の現在の質問ボタンを再登録します。
再起動前に届いたDMから、回答を続けられます。

表示更新に失敗して古い質問が残った場合は、
`resend:True` で現在の質問を再表示してください。

保存済みの結果は、保存時の判定基準を使って再表示します。
質問バージョンが異なるデータは、自動で移行・上書きしません。

### コマンドの公開範囲

`/valo_role` と `/valo_role_log` は、
診断機能が有効な登録済みサーバーにだけ登録します。

起動時に、登録済みの各サーバーへWanbotのコマンド一覧を同期します。
無効化した機能の古いコマンドも、この同期で取り除きます。
`/wanbot_status` はテストサーバー専用です。
